# Coffepoint

Учебный сервис бронирования кофеен: HTML, CSS, Vanilla JavaScript ES Modules, Firebase Authentication и Firestore. Vite отвечает за разработку и сборку. Отдельного backend, Cloud Functions и Firebase Admin SDK нет.

## Быстрый запуск в эмуляторах

Нужны Node.js 22.12+ (рекомендуется 24), Java 21+ и Chromium для браузерных тестов.

```sh
npm ci
npm run emulators
```

В другом терминале:

```sh
npm run seed:emulators
npm run dev:emulators
```

Откройте адрес Vite. Seed создаёт семь кофеен, шесть напитков и администратора:

- email: `admin@coffepoint.test`
- пароль: `DemoCoffee123!`

Это учётная запись **только локального эмулятора**. Скрипт имеет фиксированные адреса `127.0.0.1`, проект `demo-coffepoint` и не обращается к облачной базе. Повторный запуск seed обновляет демонстрационный каталог. Уже существующий Auth-аккаунт администратора не пересоздаётся.

Эмуляторы: Firestore `127.0.0.1:8080`, Auth `127.0.0.1:9099`, UI `http://127.0.0.1:4000`. Коды телефона выводятся в терминале Authentication, письма восстановления также доступны в эмуляторе. После остановки данные по умолчанию исчезают. Локальный режим предназначен для браузера на том же компьютере.

## Подключение настоящего Firebase

1. Скопируйте `.env.example` в `.env.local` и заполните четыре `VITE_FIREBASE_*` значения из настроек Web App. Установите `VITE_USE_FIREBASE_EMULATORS=false`.
2. В Firebase Console включите **Authentication → Email/Password** и **Phone**. Добавьте домен приложения в Authorized domains.
3. Создайте Firestore `(default)`. Используемый ранее проект — `coffepoint-for-college`.
4. Опубликуйте Rules и индексы:

   ```sh
   npx firebase login
   npx firebase deploy --only firestore --project YOUR_PROJECT_ID
   ```

   `npm run deploy:rules` использует прежний проект `coffepoint-for-college`. Публикуйте только в нужный вам проект. Дождитесь готовности индексов в Console.
5. Запустите `npm run dev`, войдите по телефону на `/auth.html`. При первом подтверждении номера аккаунт создаётся автоматически. Документ `users/{uid}` создастся с ролью `user`.
6. Чтобы назначить **первого** администратора, откройте этот документ в доверенной Firebase Console и измените `role` на `admin`. Самостоятельное назначение через браузер запрещено.
7. Откройте `/admin.html` и нажмите «Добавить демонстрационный каталог» либо создайте собственные кофейни и напитки. Эта кнопка работает под Rules с правами admin и добавляет только отсутствующие документы, сохраняя существующие.

Для тестового телефонного входа добавьте вымышленный номер и код в **Phone → Phone numbers for testing**. Флаг `VITE_FIREBASE_TEST_PHONE_AUTH=true` отключает reCAPTCHA только при `npm run dev`; production-сборка его игнорирует. Настоящие SMS требуют соответствующей настройки Firebase, разрешённых регионов и тарифа. Подробности: [Firebase Phone Auth](https://firebase.google.com/docs/auth/web/phone-auth).

```sh
npm run build
npm run preview
```

Для размещения используйте папку `dist` на статическом хостинге. Firebase Hosting уже настроен в `firebase.json`. Открытие HTML через `file://` не поддерживается: нужны Vite или HTTP-хостинг.

## Страницы и возможности

- `/index.html`: прежний лендинг, каталог Firestore по 6 записей, кнопка «Показать ещё», префиксный поиск названия, фильтр района, сортировка по названию или рейтингу.
- `/cafe.html?id=CAFE_ID`: сведения, часы, столики, меню, отзывы, средняя оценка гостей и переход к бронированию выбранной кофейни.
- `/booking.html?cafe=CAFE_ID`: прежняя форма с живой занятостью, датой на 30 дней вперёд, двухчасовыми интервалами, вместимостью, напитками и подтверждением телефона.
- `/auth.html`: вход и создание аккаунта по телефону; вход по ранее привязанному email и восстановление пароля. Регистрации по email в интерфейсе нет.
- `/profile.html`: имя, контакты Auth, добавление email и пароля к телефонному аккаунту, дата регистрации, выход, активные бронирования и история. Статусы обеих лент обновляются через `onSnapshot`; страницы по 10 записей.
- `/admin.html`: CRUD кофеен и напитков, статусы бронирований, фильтр статуса, пользователи и роли, удаление отзывов, статистика через `getCountFromServer`. Списки по 10 записей, обновление кнопкой. Роль текущего администратора отслеживается в реальном времени.

Вход сохраняется между страницами и перезагрузками. На общем устройстве используйте «Выйти». Ранее созданный email-аккаунт при бронировании привязывает подтверждённый телефон к **тому же UID** через `linkWithPhoneNumber`. Если телефон уже принадлежит другому аккаунту, показывается сообщение; автоматического слияния аккаунтов нет. Новые аккаунты создаются по телефону. Чтобы добавить email, используйте «Добавить email» в личном кабинете: `linkWithCredential` добавляет Email/Password к тому же UID и синхронизирует `users/{uid}`. Если адрес уже принадлежит другому аккаунту, привязка отклоняется без переключения пользователя. На странице входа способы email/телефон разделены; введённый в другой форме текст не связывает аккаунты. Подтверждение другого телефона в открытой сессии запрещено, чтобы не переключать аккаунт и не терять доступ к его профилю. Контакты профиля синхронизируются с данными токена Auth, пользователь редактирует имя. Привязанный email сохраняется в `users/{uid}`; пустое значение в последующей сессии не удаляет сохранённый адрес. Пустые email старых профилей восстанавливаются при следующем входе владельца, если адрес есть в Firebase Authentication. Админка показывает email и телефон отдельно. Пароли не сохраняются в Firestore.

## Данные и безопасность

Существующие `reservations` и `slots` сохранены. Переименовывать бронирования в `bookings` не требуется.

| Коллекция | Данные и доступ |
| --- | --- |
| `users/{uid}` | Имя, email, телефон, роль, даты. Владелец читает свой профиль и меняет имя/контакты, подтверждённые Auth. Admin читает пользователей и меняет роли **других** пользователей. |
| `cafes/{id}` | Название, `nameLower`, `searchKeywords`, описание, адрес, фото, район, особенности, часы, редакционный рейтинг, `active`, map шести столиков. Публичное чтение, запись только admin. |
| `drinks/{id}` | Название, объём, целая цена в KZT, доступность, даты. Публичное чтение, запись только admin. |
| `reservations/{uuid}` | UID, контакты, адрес и столик, гости, `startsAt`, количества напитков, сохранённая сумма, статус, даты, `slotId`. Только владелец и admin видят запись; запрос владельца содержит `where('userId', '==', uid)`. |
| `slots/{cafeId}_{tableId}_{unixSeconds}` | Только кофейня, столик, время, случайный ID брони. Публичная занятость без имени, телефона или UID. Список ограничен шестью документами. |
| `reviews/{cafeId}_{uid}` | Один отзыв пользователя о кофейне, оценка 1–5, текст и даты. Публичное чтение; владелец создаёт/редактирует/удаляет, admin может удалить любой отзыв. |

Транзакция заново читает кофейню, цены напитков и документ занятости. Rules независимо проверяют подтверждённый телефон, UID, время, вместимость, доступность, стоимость и обязательную атомарную запись брони с блокировкой столика. Изменение цены после загрузки формы требует обновить страницу и проверить сумму. Повторная отправка использует тот же UUID, а конкурирующие записи не могут занять один столик.

Переходы статусов:

- `pending → confirmed`: admin;
- `pending/confirmed → cancelled`: admin либо владелец до начала визита; отмена и удаление `slots` выполняются одной транзакцией;
- `confirmed → completed`: admin после окончания двухчасового визита;
- завершённые и отменённые записи неизменяемы. У завершённой брони историческая блокировка остаётся; она не мешает будущим датам.

Первый admin назначается только через доверенную Console. После этого администратор вправе менять роли других пользователей через приложение; Rules проверяют его текущую роль. Свою роль менять нельзя. Это защищает от случайного удаления последнего администратора через его собственный аккаунт, но не заменяет административное восстановление доступа через Console.

Публичный каталог не содержит контактов пользователей. Пользовательский текст выводится через `textContent`, DOM создаётся стандартными методами. Подписки снимаются при уходе со страницы; при смене даты/кофейни занятость переподключается.

## Запросы и индексы

Все списки приложения используют `limit` и курсоры `startAfter`; фильтр сбрасывает курсор. Каталог не загружается целиком для поиска. `searchKeywords` содержит префиксы полного названия в нижнем регистре; например, `coffepoint 0`. Это **не** поиск по подстроке в середине слова. Поля поиска пересчитываются при сохранении кофейни в админке; при ручном изменении через Console обновляйте их вместе с названием.

`firestore.indexes.json` содержит индексы реально используемых запросов:

- `slots`: `cafeId + startsAt`;
- `cafes`: восемь комбинаций `active`, необязательных `district`/`searchKeywords array-contains` и сортировки `nameLower ASC`/`rating DESC`;
- `drinks`: `available + name`;
- `reservations`: `userId + status + createdAt DESC`, `status + createdAt DESC`;
- `reviews`: `cafeId + createdAt DESC`, `cafeId + rating` для агрегации.

Single-field индексы обеспечиваются Firestore автоматически. Индексация приватных имени/телефона и map напитков в брони отключена. Эмулятор проверяет Rules и результаты запросов, но не требует composite indexes: готовность облачных индексов нужно проверить после публикации.

## Проверки

```sh
npm test
npm run test:rules
npm run test:e2e
npm run build
```

`test:rules` и `test:e2e` сами запускают эмуляторы: сначала остановите ручной `npm run emulators`, чтобы освободить порты. Тесты очищают **только** локальный `demo-coffepoint`. Браузерные тесты используют `/usr/bin/chromium`; другой путь задайте `CHROMIUM_PATH=/path/to/chromium npm run test:e2e`.

Проверяются валидация, приватность бронирований и профилей, запрет повышения собственной роли, права на отзывы и каталог, подмена цен, доступность, атомарная отмена, переходы статусов, гонка двух бронирований, курсоры. Browser-сценарии проверяют телефон, email, сохранение сессии, каталог, отзывы, XSS-текст, админку и адаптивность.

## Структура и границы проекта

- `src/firebase.js` — единственная инициализация Firebase, эмуляторы и сохранение сессии;
- `src/auth.js`, `src/ui.js` — общие функции входа/профиля и DOM;
- `src/main.js`, `src/index.js`, `src/auth-page.js`, `src/cafe.js`, `src/profile.js`, `src/admin.js` — логика страниц;
- `src/services/` — запросы кофеен, отзывов и подписки кабинета;
- `src/booking/` — сохранённый модуль бронирования; `catalog.js` содержит расписание, ограничения и исходные данные **для тестов/seed**, рабочий каталог берётся из Firestore;
- `scripts/sample-data.js`, `scripts/seed-emulators.js` — демонстрационные данные;
- `src/content.js` — тексты лендинга. Массив старых ресторанов больше не используется для каталога.

Учебные ограничения: шесть столиков, единое расписание 09:00–21:00 по Алматы, до 20 напитков и не более шести разных позиций в заказе (ограничение сохраняет проверку цен в лимите обращений Rules). Рейтинг каталога редактирует admin; **оценка гостей** на странице кофейни считается отдельно через Firestore `average/count`, без загрузки всех отзывов и без доверия клиентским счётчикам. Свободные столики показываются для конкретной даты и времени в форме, общего фильтра «свободно сейчас» нет.

Прошедшие визиты завершает admin вручную: планировщик/Cloud Functions не добавлены. Старые брони сохраняют контакты, сумму и количества напитков; исторические названия/цены отдельных позиций не денормализованы, поэтому кабинет показывает их ID. Старые `reservations` без `updatedAt` читаются и допускают разрешённый переход статуса, который добавит поле. Каталог необходимо заполнить перед использованием новой версии формы; устаревшая открытая вкладка со старым форматом брони должна быть перезагружена.

Платежи, автоматическое слияние аккаунтов, редактор схемы зала и автоматическое завершение визитов не реализованы. Для них нет необходимости усложнять текущую учебную версию. Облачные правила, индексы и Hosting не публикуются автоматически при локальной разработке.
